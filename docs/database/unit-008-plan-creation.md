# UNIT-008 — billing plan creation with profiles

`bill-plans-new.php` now calls `dalo_create_billing_plan()` on the selected PDO location. The fixed set of 21 plan fields and every selected profile mapping are written with bound values on **one connection and one transaction**. The duplicate-name check, profile existence checks and plan/mapping writes all use that PDO handle. On any mapping failure the inserted plan and all earlier mappings are rolled back. PEAR remains in the separate authentication/ACL and profile-list display paths; the shared `insert_multiple_plan_group_mappings()` is untouched because `bill-plans-edit.php` still calls it (UNIT-009).

The plan/profile table keys and RADIUS group table keys are explicitly allowlisted SQL identifiers. Submitted profiles are validated and deduplicated before writing; each name must exist in at least one group source offered by the form (`radgroupcheck`, `radgroupreply`, `radusergroup`). Non-string/nested form fields fail closed. The PlanActive form select now submits `planActive` (it previously used the second `planRecurring` name). Unknown profiles and oversized plan names fail rather than silently inserting a plan with no or incorrect mappings. The page does not expose PDO errors or bound values.

Run `PYTHONDONTWRITEBYTECODE=1 python3 tests/plan_create_http.py` using disposable PHP HTTP/MariaDB 11.8 containers and synthetic operator sessions. For the A/B comparison run the script with `PLAN_CREATE_ROOT=<PEAR snapshot>` and capture JSON, then run the candidate with `PLAN_CREATE_BASELINE_JSON=<captured JSON>`. The test compares all persisted plan fields (except generated ID/date) and mapping rows programmatically. It also checks login/ACL/CSRF, quoted/SQL-looking plan and profile names, duplicate name, malformed form fields, nonexistent profiles, no profiles, `radusergroup`-only profiles, named database location and a unique-key failure on the *second* mapping. The latter checks that both plan and first mapping are absent after rollback. No production data is touched. Existing InnoDB tables require no SQL migration.

Limitations: the schema has no unique constraint on `planName`; this unit preserves the schema, so another writer or a concurrent create under a different transaction isolation mode could still produce duplicate names. Profile mapping validity against concurrent edits outside this flow is limited by the existing lack of foreign keys. Unsupported PDO engines fail closed rather than falling back to a non-atomic PEAR write.
