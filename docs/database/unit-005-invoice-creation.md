# UNIT-005 — operator invoice creation with items

The write block in `app/operators/bill-invoice-new.php` now connects through `dalo_pdo_connect()` using the authenticated operator's selected database location. `dalo_create_invoice()` in `app/operators/library/invoice_create.php` inserts the invoice, obtains `lastInsertId()` on the **same PDO handle**, inserts all items, and commits once. Any child failure rolls back the header and earlier children. The existing PEAR connection still serves page lookups/display but performs no part of the write transaction. The shared PEAR `add_invoice_items()` remains unchanged for the separate invoice-edit page (future unit).

Invoice and item table names are from fixed configuration keys and checked as single SQL identifiers. Item values and header fields are bound using native prepared statements. The request is parsed before starting a write: blank default rows are ignored; malformed row shape, monetary values, non-scalar header/item fields, invalid status/date, and inactive or nonexistent plans are rejected. Submitted active plans are read with `FOR UPDATE` on the same PDO transaction to prevent concurrent deactivation/deletion until commit. Invalid users/types do not create invoices. Invoices without items remain supported. No PDO driver or SQL error is echoed into HTTP or debug SQL logs. Numeric amounts accept unsigned DECIMAL(10,2) values; invalid or negative values now fail closed. This deliberately differs from PEAR, which could silently insert a header despite failed items or accept malformed numeric strings via coercion. Duplicated form submissions are not deduplicated.

`dalo_pdo_connect()` currently supports only configured MySQL/MariaDB and PostgreSQL PDO drivers. Other legacy PEAR engines have no PDO implementation in UNIT-001: the create request fails without a write rather than taking a non-atomic PEAR fallback. Test those backends before enabling this staged unit there.

Verification: `PYTHONDONTWRITEBYTECODE=1 python3 tests/invoice_create_http.py` on the candidate, and the same script with `INVOICE_ROOT` pointing to a PEAR baseline on an isolated PHP HTTP/MariaDB 11.8 fixture; pass the baseline JSON file with `INVOICE_BASELINE_JSON` to compare normalized rows programmatically. The normal candidate invocation runs all candidate-only assertions. HTTP checks cover login/ACL/CSRF, a quoted string, item counts and linked ID, blank row, malformed request, zero-item invoice, named database location, and a forced duplicate-key failure on the *second* item; both header and first item roll back. No production database or NAS volume is touched. Run PHP syntax checks and `git diff --check` before commit. No SQL migration is necessary: existing InnoDB invoice tables and columns are reused.
