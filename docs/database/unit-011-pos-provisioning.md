# UNIT-011 — POS user provisioning with optional invoice

`bill-pos-new.php` now builds its RADIUS attributes, manual profiles, user information and billing information before opening **one** caller-owned PDO transaction. The transaction rechecks that the username is absent, locks an active selected plan, validates selected groups, inserts RADIUS check/reply attributes and manual/plan group mappings, then inserts `userinfo` and `userbillinfo`. When a plan was selected, the same handle inserts the invoice and its service/setup-fee items using `lastInsertId()` on that handle. Any failed operation, including a second invoice item, rolls back **all** writes. POST data is bound; table and generated column identifiers use fixed allowlists. The original password-attribute hashing, portal password hashing, disabled-group priority, computed amounts/taxes and welcome notification behavior are retained. Driver errors and submitted secrets do not enter SQL debug messages or HTTP output.

The shared PEAR `userInvoiceAdd()` function remains unchanged for the AJAX callers outside POS; calling it from this transaction would silently commit an invoice on a different connection. The POS-local invoice writes are therefore deliberate, not a migration of every `userInvoiceAdd()` caller.

Run `PYTHONDONTWRITEBYTECODE=1 python3 tests/pos_provision_http.py` on disposable PHP HTTP/MariaDB 11.8 containers and synthetic operator sessions. For an A/B run capture JSON with `POS_ROOT=<PEAR snapshot>` then run candidate with `POS_BASELINE_JSON=<captured JSON>`. The test compares normalized RADIUS attributes, group memberships, user and billing fields, invoice and both taxed items after a successful provision. Candidate-only tests cover authentication/ACL/CSRF, duplicate username, invalid/inactive plan, unknown profile, nested fields, a forced **second** invoice-item failure restoring every earlier write, no-plan creation, named location, and a portal password hash with enabled access. No live stack or production data is touched. Existing InnoDB schema needs no SQL migration.

Intentional repairs: the legacy POS removed `%` from plan names and embedded a quote-bearing name unescaped in the mapping query; selecting such a valid plan could fail with a SQL error. The candidate binds the exact stored name and provisions it successfully. A no-plan submission no longer dereferences a missing plan. The legacy form referenced an undefined `$groups` variable when redisplaying profiles after failure; it now uses `$profiles`.

Limits: other management and AJAX invoice paths still use PEAR. The schema has no unique username constraint across provisioning tables and no foreign keys for all dependencies; application checks/row locks alone cannot promise cross-writer referential integrity or concurrency-safe uniqueness. Shared identifier quoting is MySQL-style; tests exercised MariaDB, not PostgreSQL. Unsupported PDO engines fail closed rather than splitting the transaction with PEAR.
