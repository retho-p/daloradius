# UNIT-007 — invoice deletion

`app/operators/bill-invoice-del.php` uses a single PDO transaction in `library/invoice_delete.php`. The full POST selection is validated as canonical positive invoice IDs before connecting; duplicates are removed and IDs are sorted to take locks in a consistent order. For existing invoices only, the transaction locks the parent, deletes its payments and items, then deletes the invoice. Any failure rolls back **all** selected invoices, their payments and their items. Missing invoice IDs perform no write and report zero deletions. The page retains PEAR for the existing ACL and independent list-of-invoices display query, not for the write transaction. All values are bound; table identifiers are allowlisted configuration keys. The HTTP failure is generic and excludes driver/SQL details.

The PEAR baseline has two confirmed defects: deleting one invoice leaves orphan payments, and submitting IDs 51 and 52 emits `IN ('51, 52')`, so MariaDB converts the whole string to 51 and deletes only the first selected invoice. UNIT-007 intentionally differs: it deletes payments and every selected invoice atomically. A later error on the second parent's DELETE (created in the disposable database with a temporary restrictive foreign key) restores the first parent's header, items and payments as well as the second parent's dependents.

`PYTHONDONTWRITEBYTECODE=1 python3 tests/invoice_delete_http.py` runs all candidate scenarios on synthetic operator sessions, disposable PHP HTTP and MariaDB 11.8. `INVOICE_DELETE_ROOT=<PEAR snapshot> ...` runs the baseline; `INVOICE_DELETE_BASELINE_JSON=<baseline output>` compares the working single-invoice header/item state programmatically. Tests include login/ACL/CSRF, scalar/multi selection, malformed/nested/duplicate IDs, missing invoice, forced late failure, counts, unrelated invoice retention and selected database location. The baseline regressions are asserted separately. The tables are already InnoDB; no schema migration is needed. No production data or volumes are used.

As in UNIT-005/006, engines without a supported PDO driver fail closed rather than using a non-atomic PEAR fallback. Because the legacy schema has no foreign keys and other payment/item writers are not migrated by this unit, a concurrent writer that does not lock the parent could insert an orphan after deletion; full cross-page referential integrity requires those writers or a separate compatible FK migration. This unit does not claim to solve that race.
