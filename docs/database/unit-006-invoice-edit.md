# UNIT-006 — invoice edit with item replacement

The `bill-invoice-edit.php` write block now uses `dalo_replace_invoice_items()` on the configured PDO location. One transaction locks the existing invoice and selected active plans, updates its submitted header fields and audit metadata, deletes the former items, inserts all replacement items, then commits. A missing invoice, invalid input, or any child failure rolls back header, deletion, and prior child inserts. Payments remain untouched. PEAR still provides ACL, option and display reads before/after the PDO transaction; no PEAR statement is part of this write transaction. The old shared PEAR `add_invoice_items()` is not called by create/edit, but retained for any other users.

The edit form now selects the stored active plan rather than silently selecting the first plan for every item. Item parsing and plan locking reuse UNIT-005 helpers. Header values are bound; optional empty edit fields retain their prior skip-update behavior, including the existing inability to clear notes with an empty string. Invalid nonempty/malformed fields fail closed. Only fixed configuration table keys are accepted and SQL errors do not reach HTTP.

The PEAR baseline has a concrete bug: its header UPDATE uses an undefined `$invoice` rather than `$invoice_id`, so it updates `WHERE id=0` while still replacing children and reporting success. Consequently the valid child snapshot matches PEAR, but UNIT-006 intentionally updates the header. `tests/invoice_edit_http.py` verifies both against equivalent disposable MariaDB/PHP sessions, then on the candidate tests login/ACL/CSRF, invalid form fields, named database location, empty replacement, unchanged payments, and a forced failure on the *second* insert after deletion. The before/after snapshot includes header audit fields, every item and payments. Re-run UNIT-005 tests after changes to its shared plan-lock helper. This is isolated real HTTP/database validation, not a production test. No schema migration is required; InnoDB tables are already transactional. As with UNIT-005, engines without a supported PDO driver fail closed rather than taking a non-atomic PEAR fallback.
