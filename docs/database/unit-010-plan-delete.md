# UNIT-010 — billing plan deletion

`bill-plans-del.php` now validates the entire scalar/multi selection, deduplicates and sorts names for consistent lock ordering, then uses a single PDO transaction to lock selected plans, remove their profile mappings, and finally remove the plans. Prepared statements bind all submitted names; dynamic table identifiers pass through UNIT-008's fixed allowlist. A malformed, stale, or unknown name aborts the whole selection rather than silently deleting the other names. A late database error rolls back earlier plan/mapping deletions. Success counts report affected plan and mapping rows, not a cast of a PEAR result resource: the PEAR baseline reported `Deleted 1 plan(s)` for a successful two-plan deletion, although both rows were removed. This output change is intentional; surviving SQL state matches. Authorization and CSRF checks remain on the page. The option list is still read by PEAR outside the write transaction; this read neither authorizes the deletion nor participates in its transaction.

The GET preselection preserves a stored plan name containing `%` instead of removing it, so plans created by UNIT-008 with that character can be selected for deletion.

Run `PYTHONDONTWRITEBYTECODE=1 python3 tests/plan_delete_http.py` with disposable PHP HTTP/MariaDB 11.8 containers and synthetic sessions. For A/B comparison, capture JSON using `PLAN_DELETE_ROOT=<PEAR snapshot>` and then run the candidate with `PLAN_DELETE_BASELINE_JSON=<captured JSON>`. The test compares the complete surviving plan columns and profile associations after single and multi-plan deletion, and separately covers authentication, ACL, CSRF, malformed and stale selections, repeated names, quote/percent-bearing names, named location, and an injected foreign-key failure on a **later** plan after an earlier plan and its mappings are deleted. All rows are restored by rollback. No production data or live stack is used; existing InnoDB schema requires no migration SQL.

Limits: other billing plan consumers/writers remain outside this unit. Without foreign keys from the mapping table, independent legacy writers can insert an orphan association after deletion despite the parent lock. No referential cleanup beyond `billing_plans_profiles` is attempted. MySQL-style identifier quoting in the shared plan helper has been tested on MariaDB, not PostgreSQL; unsupported PDO engines fail closed rather than falling back to a separate PEAR write.
